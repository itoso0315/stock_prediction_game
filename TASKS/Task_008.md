

# TASK 008 - 次の問題へ進む

## 1. Taskの目的
- 回答結果を確認後、「次の問題」ボタンを追加する。
- ユーザーが解答後、すぐに新しい問題に進めるようにする。
- 既存のアーキテクチャを維持したまま、次の問題に必要なstateのみリセットする。

## 2. ゴール
- 回答後に「次の問題」ボタンを押すと、新しいGameQuestionが生成される。
- 直前の問題・回答内容は破棄される。
- アプリは「未回答の新しい問題が出ている」状態に戻る。

## 3. 実装対象
- 「次の問題」ボタンの追加。
- Session State（`game_question`, `answer_choice`, `selected_label`, `submitted`）のリセット。
- 新しい問題の生成。
- 既存の `select_random_tickers()` と `generate_game_question()` を通常の乱数設定で再利用する。追加の重複防止や重み付けは行わない。偶然前回と同じ内容の問題が生成されても正常動作とする。
- 問題生成失敗時は部分的な表示をせず、既存のエラーメッセージのみ出す。
- 既存APIはそのまま利用する。

## 4. 今回の対象外
- スコア機能
- 回答履歴
- 連続正解（streaks）
- 結果画面の設計変更
- 別ページへの遷移
- AIによる解説
- 回答前の企業情報開示
- カードクリックUIの改善
- ユーザーアカウント
- 永続的なストレージ

## 5. 作成・変更予定のファイル
- `app.py` のみを修正。
- 既存のモジュール・APIは再利用する。
- 新しいファイルは作成しない。

## 6. Session State
- `game_question`: キー未生成（Noneは使用しない）
- `answer_choice`: None
- `selected_label`: None
- `submitted`: False

### (b) 回答後
- `game_question`: 現在の問題
- `answer_choice`: ユーザーの選択
- `selected_label`: 選択されたラベル
- `submitted`: True

### (c) 「次の問題」クリック後
- `game_question`: 新しい問題
- `answer_choice`: None
- `selected_label`: None
- `submitted`: False


## 7. ボタン仕様
- submitted=True のときのみ「次の問題」ボタンを表示する。
- ボタンラベルは「次の問題」。
- ボタンには一意のkeyとして `next_question` を設定する。
- クリック時は新しいGameQuestionをローカル変数として生成する。生成成功を確認してからSession State（game_question・answer_choice・selected_label・submitted）をまとめて更新し、st.rerun()で未回答画面へ戻る。
- 確認ダイアログ等は不要。

## 8. app.py処理順
1. Session Stateの初期化
2. 問題（GameQuestion）の生成
3. ユーザーによる解答・送信
4. 結果表示（正誤判定等）
5. `submitted=True` なら「次の問題」ボタンを表示
6. 「次の問題」クリック時は、新しいGameQuestionをローカル変数として生成する。
7. 生成成功後にのみ game_question・answer_choice・selected_label・submitted をまとめて更新する。
8. 更新後に st.rerun() を実行し、未回答画面へ戻る。

## 9. エラー処理
- 問題生成失敗時は旧結果画面を残したまま、「問題データを生成できませんでした。時間をおいて再度お試しください。」を追加表示する。
- 部分的なUI表示や中途半端なstateリセットは絶対にしない。
- 新しい問題の生成に失敗した場合は現在の問題を保持し、Session Stateを変更しない。
- 新しいGameQuestionの生成成功後、Session Stateを更新する前に、その問題の3つの表示用Figureをローカルで事前生成して表示可能であることを確認する。
- 新しい問題の表示用Figureを1つでも生成できない場合は、新しい問題への切り替えを行わず、旧問題・旧回答・旧結果画面を保持する。
- 事前確認に失敗した場合も `st.rerun()` は呼び出さず、利用者は再度「次の問題」を押せる。

## 10. 既存APIとの整合性
- 既存のAPI・関数名・クラス名は変更しない。
- `app.py` で `yfinance` を直接importしない（既存モジュール経由のみ）。

## 11. 実装手順
1. `app.py` で `submitted=True` の場合のみ「次の問題」ボタンを表示する処理を追加。
2. ボタン押下時に新しいGameQuestionをローカル変数として生成する。
3. 新しいGameQuestionの3つの表示用Figureをローカルで事前生成し、すべて表示可能であることを確認する。
4. 問題生成とFigure事前生成の両方に成功した場合のみ、Session Stateの4状態をまとめて更新する。
5. 更新後に `st.rerun()` を実行する。
6. 問題生成またはFigure事前生成に失敗した場合はSession Stateを変更せず、旧結果画面を保持したまま指定エラーメッセージを追加表示する。

## 12. 受け入れ条件
- 「次の問題」ボタンに `next_question` の一意なkeyが設定されている。
- 新しい問題は既存APIを使い `period="5y"` で生成される。
- 新しい問題の3つの表示用Figureがすべて生成可能であることを確認してからSession Stateを更新する。
- 新しい問題のFigure事前生成に失敗した場合、旧問題・旧回答・旧結果画面を保持する。
- 問題生成またはFigure事前生成に失敗した場合、`st.rerun()` を呼び出さない。
- 問題生成失敗時は旧結果画面に指定エラーメッセージを追加表示し、再度「次の問題」を押せる。
- 新問題への切り替え後、旧正誤結果・旧騰落率・旧将来チャートが表示されない。
- `app.py` 以外のファイルを変更していない。
- `app.py` からyfinanceを直接importしていない。
- 既存公開APIを変更していない。
- 自動テストファイルを新規作成していない。
- 回答前は「次の問題」ボタンが表示されない。
- st.rerun()後は未回答画面へ戻る。
- 偶然前回と同じGameQuestionが生成されても正常動作とする。
- 問題生成失敗時は旧問題・回答状態・結果画面を保持する。
- 問題生成失敗時は「問題データを生成できませんでした。時間をおいて再度お試しください。」のみ表示する。
- 回答後のみ「次の問題」ボタンが表示される。
- ボタン押下で新しいGameQuestionが生成される。
- 直前の回答内容が消去される。
- `submitted=False` になる。
- 前の問題や回答内容が残らない。
- 必要なSession Stateが正しくリセットされる。
- 新しい問題の生成に失敗した場合、現在の問題・回答状態が保持される。
- Python文法エラーがないこと（`python -m py_compile app.py`）。
- `git diff --check` で差分にスペース・タブ等の問題がないこと。
- `streamlit run app.py` でアプリが起動し、次の問題に進めること。

## 13. 動作確認
1. アプリを起動し、1問目に回答・送信する。
2. 回答結果が表示され、「次の問題」ボタンが出現することを確認。
3. ボタンを押すと、新しい問題に切り替わることを確認。
4. 以前の問題・回答内容が残っていないことを確認。
5. 何度でも次の問題に進めることを確認。
6. 問題生成失敗時はエラーメッセージのみ表示されることを確認。
7. 回答前に「次の問題」ボタンが表示されないこと。
8. 回答後だけ「次の問題」ボタンが表示されること。
9. ボタンkeyが `next_question` であること。
10. 新問題の3銘柄がすべて `period="5y"` で取得されること。
11. 新問題生成成功前に4つのSession Stateが変更されないこと。
12. 新問題の3つの表示用Figureがすべて生成可能であることを確認してから4状態が更新されること。
13. 更新後に `st.rerun()` が1回だけ呼ばれること。
14. 問題生成失敗時に4状態が不変で、旧結果画面と「次の問題」ボタンが残ること。
15. Figure事前生成失敗時に4状態が不変で、旧結果画面と「次の問題」ボタンが残ること。
16. 失敗時に `st.rerun()` が呼ばれないこと。
17. 成功後の未回答画面に旧正誤結果・旧騰落率・旧将来チャートが残らないこと。
18. 偶然前回と同じ問題内容でも正常に切り替わること。
19. 複数回連続して次の問題へ進めること。
20. Git差分が `app.py` だけであること。
21. `app.py` にyfinanceの直接importがないこと。
22. 既存公開APIが維持されていること。
