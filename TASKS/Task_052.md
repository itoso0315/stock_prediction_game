

# Task 052: 出題バランス制御と10問連続プレイを実装する

## 目的
Stock Trainerを「1問ずつのデモ」から、10問連続で遊べる学習ゲームへ進化させる。

あわせて、現実の相場に近い判断体験を作るため、出題パターンを以下の2種類に制御する。

さらに、10問終了後の最終Result画面に共有機能を追加し、プレイ結果をX、Instagram、LINE、URL共有で外部へシェアできるようにする。

- 通常問題：Chart A / B / Cのうち1銘柄のみ1か月後騰落率がプラス、残り2銘柄はマイナス
- 現金問題：Chart A / B / Cすべての1か月後騰落率がマイナスで、現金保有（0.0%）が正解

この内部ルールはユーザーには開示しない。

## 設計思想

ゲームの選択肢は以下の4つを維持する。

```text
Chart A
Chart B
Chart C
現金保有
```

内部的な出題比率は以下とする。

- 現金問題：ゲームごとに0〜3問
- 通常問題：現金問題以外の7〜10問

10問セット生成時に現金問題数を0・1・2・3問からランダムに選択し、
ゲームごとの現金問題比率を0%・10%・20%・30%のいずれかにする。

### 正答率に関する考え方

4択を完全ランダムに選んだ場合の期待正答率は25%。

通常問題と現金問題の比率にかかわらず、4択を完全ランダムに選ぶ限り期待正答率は25%のまま。

一方、内部ルールを推測して現金保有を一切選ばず、通常問題のみ3択で当てにいくようなプレイでは理論上の期待正答率は約26.7%になる。

そのため、将来のスコア設計では25%前後をランダム相当の目安として扱える。

Task052では、この思想を壊さない出題ロジックと10問連続プレイを実装する。

## 現在地

- Question画面ではChart A / B / Cに実在日本株のチャートを表示できる。
- 過去120営業日（約半年）を見て、約1か月後を予測する仕様へ移行している。
- 出来高を表示できる。
- 「移動平均線 ON／OFF」ボタン1つでMA20 / MA40 / MA70をまとめてON/OFFできる。
- Result画面では過去＋未来を連続表示し、予測時点を点線、過去領域を薄い灰色背景で示す仕様がある。
- Result画面では正解を緑、不正解を赤で表示する仕様がある。
- Chart A / B / C / 現金保有の4択を維持する。
- 現在は問題数が少なく、10問連続プレイとしては未完成。

## 実装内容

### 1. 通常問題と現金問題の2パターンを定義する

#### 通常問題
1か月後の実データ騰落率が以下の条件を満たす3銘柄を選定する。

- 1銘柄：騰落率 > 0%
- 2銘柄：騰落率 < 0%

正解はプラスの1銘柄。

#### 現金問題
1か月後の実データ騰落率が以下を満たす3銘柄を選定する。

- Chart A < 0%
- Chart B < 0%
- Chart C < 0%

この場合、現金保有（0.0%）を正解とする。

### 2. 出題条件はユーザーへ開示しない

Question画面には以下を表示しない。

- 「必ず1銘柄上がります」
- 「この問題は現金問題です」
- 通常問題/現金問題の出題比率
- 正解候補数に関するヒント

ユーザーには従来どおり、

```text
基準日時点のチャートを見て、
評価日までに最も上昇すると思うものを選んでください。
```

程度の自然な問題文だけを表示する。

### 3. 現金問題を0〜30%でランダムに構成する

- 現金問題数を0・1・2・3問からランダムに選ぶ。
- 残りを通常問題とする。

実データで条件確認済みの通常問題候補と現金問題候補から10問を選定する。
銘柄のChart A/B/Cへの割当は起動時にランダム化する。

### 4. 条件に合う実在日本株を実データから選定する

株価や騰落率を人工的に加工して条件へ合わせてはならない。

必ず実際の過去データから、条件を満たす銘柄・基準日・評価日の組み合わせを選ぶ。

要件：
- 日本株を対象とする。
- 将来的には日経225採用銘柄プールを前提とする。
- Chart A / B / Cは互いに異なるticker。
- 同一Question内では同一baseDate / evaluationDateを使用する。
- 基準日までの過去120営業日をQuestion画面へ表示する。
- 未来データはQuestion画面へ漏らさない。
- 評価日の騰落率で出題条件を判定する。

### 5. 正解の位置を固定しない

通常問題でプラス銘柄が毎回Chart A等に固定されないようにする。

条件を満たした3銘柄は、Questionへ割り当てる際にA/B/Cの位置をランダム化する。

現金問題でも、A/B/Cの並びに規則性を持たせない。

### 6. 10問連続プレイへ変更する

1ゲームを10問構成とする。

```text
Question 1 / 10
Question 2 / 10
...
Question 10 / 10
```

要件：
- 1回のゲーム開始で10問を遊べる。
- 各問で回答 → Result → 次の問題へ進む。
- 10問終了後にゲーム全体の結果画面へ進む。
- 問題番号表示を10問仕様へ対応させる。
- 途中でQuestion / Result遷移が壊れない。
- MA表示状態はQuestionを移動しても維持する。

### 7. 10問内で同じ問題を重複させない

同一10問セット内で、完全に同じ問題を繰り返さない。

少なくとも以下の組み合わせが同一にならないようにする。

- baseDate
- Chart A / B / Cのticker構成

可能であれば、同じtickerが短期間に繰り返し出すぎないようにも配慮する。

### 8. 問題生成失敗時の扱い

条件検索では、該当する銘柄セットがすぐ見つからない可能性がある。

要件：
- 無限ループしない。
- 最大試行回数等の安全策を設ける。
- 条件に合う候補が見つからなかった場合は、固定ダミー株価へ黙ってフォールバックしない。
- 既存のBackendエラー方針に従い、原因が分かる形で失敗させる。
- 将来的に事前生成/キャッシュへ移行しやすい構造にする。

### 9. API呼び出し回数とパフォーマンスに配慮する

10問 × 3銘柄を毎回Yahoo Financeへ逐次取得すると非常に遅くなる可能性がある。

Task052では、実用上必要であれば以下のいずれかを導入してよい。

- 同一ticker/期間のメモリキャッシュ
- 候補株価データの一括取得
- 10問セットの事前生成
- 既存取得結果の再利用

ただし、大規模な永続キャッシュ基盤はTask052の必須要件ではない。

10問開始までの待ち時間が現実的な範囲に収まることを優先する。

### 10. 正答数をゲーム中に保持する

10問プレイ中、ユーザーの正解数を保持する。

最低限以下を内部状態として持つ。

- 現在の問題番号
- 正解数
- 各問のユーザー回答
- 各問の正誤

既存のAnswerRecord等が利用できる場合は再利用する。

### 11. 10問終了後の最終結果

Question 10のResult確認後、ゲーム全体の結果画面へ進む。

最低限以下を表示する。

```text
10問中 4問正解
正答率 40%
```

正答率は、

`正解数 / 10 × 100`

で計算する。

Task052では高度なランキング・レベル判定は不要。

### 11-1. 最終Result画面に共有機能を追加する
10問終了後の最終Result画面に、プレイ結果を外部へ共有するための共有エリアを追加する。

最低限以下の共有導線を用意する。

- X
- Instagram
- LINE
- URL共有

共有内容には、少なくとも以下を含める。

- 10問中の正解数
- 正答率
- Stock Trainerを遊んだ結果であること
- アプリまたはWeb版へ戻れる共有URL

共有文面の例：

```text
Stock Trainerで10問中4問正解！
正答率40%でした📈

#StockTrainer
<共有URL>
```

要件：
- 最終Result画面から共有操作できる。
- 各SNSのボタンを並べても画面が過密にならないよう、コンパクトな共有UIにする。
- X / LINEは可能な範囲で投稿文とURLを引き渡せるようにする。
- Instagramはプラットフォーム制約を確認し、直接テキスト投稿が難しい場合はOS標準共有シート経由や画像共有など、現実的な方法を採用する。
- URL共有はOS標準共有シートまたはコピー操作で共有できるようにする。
- Web版URLが利用可能な場合は、そのURLを共有対象に使用する。
- iOS / macOS / Webで共有仕様が完全に同一でない場合は、既存Flutter構成に合わせて実用的な方法を優先する。
- 共有失敗でゲーム本体がクラッシュしないようにする。
- 共有機能のためにQuestion / Resultの既存ゲームロジックを変更しない。

将来的にOGP画像や結果画像カードを生成してSNS共有する拡張を想定できる構成にするが、Task052では必須としない。

### 12. ランダム相当25%を今後使える設計にする

将来的にスコア評価へ以下の考え方を利用できるよう、正答率データを扱いやすくしておく。

目安：

```text
25%前後  ランダム回答相当
30〜40%  ランダム以上
50%以上  高い正答率
```

Task052ではこの評価ラベルをUI表示することは必須ではない。

正答数・正答率を正しく保存/計算できればよい。

### 13. テストを追加・更新する

Backend：
- 通常問題が「1プラス・2マイナス」を満たす。
- 現金問題が「3銘柄すべてマイナス」を満たす。
- 現金問題では正解が現金保有になる。
- 通常問題ではプラス銘柄が正解になる。
- Chart A/B/Cの位置に正解が固定されない。
- QuestionレスポンスにproblemType等の内部ヒントを不必要に露出しない。
- A/B/Cが異なるticker。
- 同一QuestionでbaseDate/evaluationDateが一致する。
- 120営業日＋1か月後というTask051のルールを維持する。
- 10問生成できる。
- 同一問題の完全重複がない。
- 条件探索に安全な最大試行制御がある。

Flutter：
- Question 1 / 10〜Question 10 / 10まで進める。
- A/B/C/現金保有の4択を維持する。
- 各問でResultを確認後、次のQuestionへ進める。
- 10問目終了後にゲーム全体の結果画面へ進む。
- 正解数を正しく集計できる。
- 正答率を正しく計算できる。
- 10問中10問正解なら100%。
- 10問中0問正解なら0%。
- 10問終了後の最終Result画面に共有UIが表示される。
- X / Instagram / LINE / URL共有の各導線が存在する。
- 共有文面に正解数・正答率・共有URLを含められる。
- 共有操作を行ってもゲーム本体がクラッシュしない。
- 既存Question / Resultチャートが壊れていない。
