# Task 050: Result画面を実データの答え合わせチャートへ刷新する

## 目的
問題画面で予測したChart A / B / Cについて、予測時点までに見えていた過去チャートと、その後約3か月の実際の値動きをResult画面で連続して表示し、「予測後に実際どうなったか」を直感的に振り返れる答え合わせ画面を作る。

単に正解・不正解や騰落率を表示するだけではなく、予測基準日を境に未来の値動きを開示することで、チャートを見て予測し、結果から学ぶというゲームの中心的な学習体験を完成させる。

## 現在地
- Question画面ではChart A / B / Cすべてに実在日本株のチャートを表示できる。
- A/B/Cは同一Question内で同じ基準日を使用する。
- 各Chartには基準日までの過去60営業日のOHLCと出来高を表示する。
- カード外の共通ボタンでMA20 / MA40 / MA70を一括ON/OFFできる。
- 問題画面では銘柄名・ticker・基準日以降の未来情報を隠している。
- 問題文には、ユーザーが予測対象期間を明確に理解できるよう「基準日」と「評価日」を表示する仕様とする。
- Chart A / B / C / 現金保有の4択から回答できる。
- Result画面はまだ完成仕様ではなく、Chart A/Bのみなどダミー中心の表示が残っている。

## 実装方針
Backendから、問題時に表示した過去60営業日と基準日より後の約3か月の実データをResult用として返す。

Result画面ではChart A / B / Cをすべて表示し、各Chartについて過去と未来を一本の連続したチャートとして描画する。

Question画面のチャート機能・回答操作は変更しない。ただし問題文には基準日と評価日を追加表示する。

### 0. Question画面の問題文に基準日と評価日を表示する
問題文の中で、ユーザーが「いつの時点までのチャートを見て、いつまでの値動きを予測するゲームなのか」を明確に理解できるようにする。

少なくとも以下をQuestion画面に表示する。

- 基準日：問題画面で表示しているチャートの最終日
- 評価日：騰落率を判定する将来の取引日

表示イメージ：

```text
基準日：2024/05/01
評価日：2024/08/01

基準日時点のチャートを見て、
評価日までに最も上昇すると思うものを選んでください。
```

要件：
- A/B/Cで共通の基準日を表示する。
- Resultの騰落率計算に実際に使用する評価日を表示する。
- 評価日が休日・休場日の場合は、Backendで実際の判定に使用する取引日とQuestion画面の表示を一致させる。
- 基準日・評価日を表示しても、銘柄名・ticker・基準日以降の株価など答えにつながる未来情報はQuestion画面へ表示しない。
- 問題文は既存UIに自然に追加し、チャート領域を不必要に圧迫しない。
- Question画面とResult画面で基準日・評価日の値が一致すること。

### 1. Result用の将来株価データをBackendで取得する
- Chart A / B / Cそれぞれについて、問題画面で使用した基準日より後の実際の株価データを取得する。
- 評価期間は基準日から約3か月後を基本とする。
- 基準日以前の問題表示用60営業日と、基準日以降の将来期間をResult用に連続して扱えるようにする。
- A/B/CはQuestion画面で使用したものと同じticker・同じbaseDateを使用する。
- Result用データに別銘柄や別基準日が混入しないようにする。
- データは日付昇順とする。

### 2. 評価日と騰落率を実データから計算する
各Chartについて、基準日の終値を基準として評価日までの騰落率を計算する。

概念：

`騰落率 = (評価日の終値 / 基準日の終値 - 1) × 100`

要件：
- Chart A / B / Cそれぞれの騰落率を計算する。
- 現金保有の騰落率は0.0%とする。
- 評価日は「基準日から約3か月後」に対応する実際の取引日を使用する。
- 休日・休場日に当たる場合は取得可能な適切な取引日を使用する。
- Result画面に表示する騰落率と正解判定に使う値を一致させる。

### 3. 正解を実データから決定する
Chart A / B / C / 現金保有の4つの騰落率を比較し、最も高いものを正解とする。

例：

```text
Chart A      +12.4%
Chart B       -5.8%
Chart C      +21.3%  ← 正解
現金保有       0.0%
```

A/B/Cがすべてマイナスの場合、0%の現金保有が正解になり得る。

同率1位が発生した場合は、既存仕様を確認したうえで破綻しない扱いにする。必要以上に複雑なルール追加はしない。

### 4. Result画面にChart A / B / Cをすべて表示する
現在Result画面にChart A/Bしか存在しない場合はChart Cを追加する。

Result画面には必ず以下を表示する。

- Chart A
- Chart B
- Chart C
- 現金保有の結果

A/B/Cの結果カードは可能な限り共通Widgetを利用し、同じ表示仕様にする。

### 5. 過去＋未来を一本の連続チャートとして表示する
各Chartについて以下を一つのチャートとして表示する。

```text
問題時に見えていた過去60営業日       予測対象だった未来 約3か月

────────────────│────────────────────
                ↑
             予測基準日
```

要件：
- 左側はQuestion画面で実際に表示していた過去データ。
- 右側は回答時には見えていなかった将来データ。
- 過去と未来で日付の連続性を維持する。
- 基準日を境にチャートが不自然に途切れないようにする。
- ローソク足を基本とする。
- Result画面では未来を含むため、Question画面用データとResult用データの責務を混同しない。

### 6. 予測基準日を明確に表示する
チャート上で「ここまでが問題画面で見えていた」という境界を一目で理解できるようにする。

- 基準日の位置へ縦線などの明確な区切りを表示する。
- `予測時点` 等の短いラベルを表示してよい。
- 過去領域と未来領域の違いが直感的に分かるようにする。
- ただし未来側を派手に装飾しすぎず、実際の値動きを読みやすくする。

### 7. 各Chartの騰落率を分かりやすく表示する
各Chartの結果カードに、基準日から評価日までの騰落率を目立つ形で表示する。

例：

```text
Chart C
+21.3%
```

要件：
- 正負が一目で分かる。
- 小数桁は既存UIとの整合を見て読みやすく整える。
- 数値をチャートに重ねて読みにくくするのではなく、カード内の適切な位置へ表示する。

### 8. ユーザーの選択と正解を識別できるようにする
Result画面で少なくとも以下が分かるようにする。

- ユーザーが選択した選択肢
- 実際に最も騰落率が高かった正解
- ユーザーの回答が正解だったか不正解だったか

既存の正解/不正解UIが利用できる場合は再利用する。

正解カードとユーザー選択カードが同一の場合も表示が破綻しないようにする。

### 9. Result画面で銘柄情報を開示する
問題画面では隠していた情報を答え合わせとしてResult画面で開示する。

各Chartについて少なくとも以下を表示できる構成にする。

- 銘柄名
- ticker / 銘柄コード
- 基準日（Question画面に表示したものと同一）
- 評価日（Question画面に表示したものと同一）

情報量が多くなりすぎないよう、チャート学習を主役とした表示にする。

### 10. 現金保有の結果を表示する
現金保有はチャートを持たない。

Result画面では独立した結果カード等で、

```text
現金保有
0.0%
```

と分かりやすく表示する。

現金保有が正解の場合は正解として識別できるようにする。
ユーザーが現金保有を選択した場合も選択結果を表示する。

### 11. 出来高の扱い
Resultチャートでも、可能な限り問題画面と同様に出来高を表示する。

- 過去60営業日＋未来期間のVolumeを連続表示する。
- ローソク足とX座標を一致させる。
- Result画面が過密になる場合でも、価格チャートの視認性を優先する。

### 12. 移動平均線の扱い
Task050ではResult画面のMA ON/OFFを必須要件としない。

まずは、
- 過去＋未来チャート
- 予測基準日の境界
- 騰落率
- A/B/C/現金の比較
- 銘柄情報開示

を優先する。

既存実装を簡単に再利用できる場合のみMA対応を追加してよいが、Task050の完了を妨げる複雑化はしない。

### 13. API契約を整理する
Result画面に必要な将来データを追加する際、Question画面へ未来データを誤って露出させないことを最優先とする。

- Question画面用レスポンスでは従来どおり基準日以降の未来情報を見せない。
- Result画面でのみ将来データへアクセスできる構成にする。
- 既存APIを無理に巨大化させるより、必要であればResult専用レスポンス/エンドポイントを追加してよい。
- 既存Flutterコードとの互換性を不必要に壊さない。

### 14. テストを追加・更新する
少なくとも以下を確認する。

Backend：
- A/B/CすべてにResult用将来データが存在する。
- Question画面用データに未来データが混入しない。
- Result用データがQuestionと同じticker/baseDateを使用する。
- 過去＋未来が日付昇順。
- 評価日が基準日より後である。
- 騰落率が実データから正しく計算される。
- 現金保有が0%。
- 4択から最高騰落率を正解として判定できる。

Flutter：
- Question画面の問題文に基準日と評価日が表示される。
- Question画面とResult画面で基準日・評価日が一致する。
- Result画面にChart A/B/Cがすべて表示される。
- 各Chartに過去＋未来の連続チャートが表示される。
- 予測基準日の境界が表示される。
- 各Chartの騰落率が表示される。
- 現金保有0%が表示される。
- ユーザー選択と正解を識別できる。
- 銘柄情報をResultで表示できる。
- Question画面の既存機能が壊れていない。
